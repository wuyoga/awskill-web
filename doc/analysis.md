# awskill 产品分析与决策记录

> 文档状态：初版
> 目标：整理现有讨论和原型中已经落地的产品判断，为正式开发提供统一上下文。

## 1. 背景与产品命题

awskill 是面向中文 AI Agent 重度用户的 Skill 评测与发现平台。品牌含义为 **Agent Workflow Skills**，域名为 `awskill.com`。

产品需要解决的不是“哪里有更多 Skill”，而是用户在安装前无法可靠回答以下问题：

1. 这个 Skill 能否在我使用的 Agent 上正常工作？
2. 它会读取、修改或删除哪些内容，是否会访问网络或凭据？
3. 热度之外，它在真实任务中的表现是否优于不用 Skill？
4. 安装方式、依赖、成本和输出是否符合我的环境？
5. 多个 Skill 能否按顺序组合成可复用的完整工作流？

因此，核心定位确定为：

> 不只看热度，安装前先确认兼容性、安全风险和真实任务表现。

## 2. 目标用户与核心场景

### 2.1 优先用户

- 同时使用一个或多个编码 Agent 的中文开发者。
- 经常尝试社区 Skill、Prompt、Rule 或自动化工作流的高级用户。
- 团队内负责 AI 工具选型、安全评估或效率建设的工程师。
- 希望通过可复用工作流完成设计、研发、测试、内容等任务的独立创作者。

### 2.2 典型任务

- 按任务、Agent、风险和输出格式寻找 Skill。
- 安装前查看四个 Agent 的兼容性矩阵。
- 查看权限原因、安全结论、验证 Commit 和结论是否过期。
- 比较 2–3 个候选 Skill。
- 阅读包含测试环境、验收标准、运行结果和证据的评测。
- 按目标选择工作流，并为指定 Agent 生成逐项安装命令。
- 收藏候选 Skill，后续接收更新或重新验证提醒。

## 3. 当前原型盘点

### 3.1 技术现状

当前仓库是 React + Vite 原型，并非正式目标架构：

- React 19、Vite 8、TypeScript 5.7、Tailwind CSS 4。
- 数据保存在 `src/data.ts` 和 `src/data-en.ts`。
- `src/useData.ts` 负责中英文数据组装和双语搜索索引。
- `src/i18n.tsx` 负责枚举及界面文案的中英文切换。
- 使用 hash 路由，没有服务端渲染、正式 URL、CMS 或后端 API。
- 收藏、语言和主题保存在 `localStorage`。
- 登录、提交 Skill、评测证据、安全指南等入口仍为原型占位。

### 3.2 已实现页面与路径

| 页面 | 原型路径 | 当前能力 |
| --- | --- | --- |
| 首页 | `#/` | 品牌定位、全局搜索、热门任务、Agent 入口、验证 Skill、分类和安全说明 |
| Skill 发现 | `#/search` | 双语关键词匹配、分类与多维筛选、排序、移动端筛选抽屉 |
| Skill 详情 | `#/skill/:id` | 兼容性、安全权限、安装方案、使用场景、评测关联、收藏 |
| Skill 对比 | `#/compare` | 最多 3 个 Skill，对比表横向滚动 |
| 评测中心 | `#/reviews` | 评测列表、分类筛选、评测方法说明 |
| 评测详情 | `#/review/:id` | 固定任务、环境、分维度结果、运行记录和证据入口 |
| 工作流中心 | `#/workflows` | 推荐工作流和按目标浏览 |
| 工作流详情 | `#/workflow/:id` | 步骤、输入输出、组合风险、按 Agent 生成安装命令 |
| Agent 中心 | `#/agents` | 四个 Agent 的说明、覆盖数量与安装差异 |

### 3.3 已落地交互

- 中英文切换和深浅主题。
- `Ctrl/Cmd + K` 聚焦全局搜索。
- 查询词、10 个任务分类、Agent、验证状态、安全等级、使用要求、输出格式筛选。
- 综合推荐、最近验证、最多使用、最新收录排序。
- 移动端底部筛选抽屉。
- 最多 3 个 Skill 的对比栏与对比页。
- 收藏本地持久化。
- Agent 兼容矩阵在窄屏压缩显示。
- 方案 B 安装：针对 Agent 输出不同命令、目录、格式和卸载命令。

### 3.4 原型数据边界

当前 Skill 数据已经验证了正式数据模型的主要方向，包括：

- 基础信息：名称、仓库、作者、分类、标签、说明、许可证。
- 兼容性：Agent、支持状态、Agent 版本、操作系统、验证时间和备注。
- 安全：风险等级、风险摘要、六类权限及原因。
- 验证：任务实测、安装验证、待验证。
- 使用要求：API Key、付费、Shell、网络、前置条件。
- 结果：输出格式、安装量、星标、收录时间。
- 可追溯性：验证 Commit、最新 Commit、结论过期状态。
- 安装：各 Agent 的安装、卸载、目标目录和格式。
- 评测：任务、验收条件、参与者、环境、分维度结果、运行记录和证据。
- 工作流：步骤、输入、输出、Skill 关系、整体验证 Agent 和组合风险。

原型中的目录数量、安装量、星标、评测结果和相对日期均为演示信息，正式系统必须改为 CMS、同步任务或评测流程产生的真实数据。

## 4. 分类与筛选推导

### 4.1 一级任务分类

已确定为 10 个任务型一级分类：

1. 开发与工程
2. 设计与用户体验
3. 测试与安全
4. 数据与研究
5. 内容与文档
6. 视觉与多媒体
7. 营销与增长
8. 产品与业务
9. 生产力与自动化
10. Agent 与工具链

分类用于回答“我要完成什么任务”，不承担兼容性、安全性或输出形态的表达。

### 4.2 独立筛选维度

- Agent：Claude Code、Codex、Cursor、Windsurf。
- 验证状态：任务已实测、安装已验证、待验证。
- 安全等级：低风险、中风险、未评估。
- 使用要求：无需 API Key、免费使用、无需执行 Shell、无需访问网络。
- 输出格式：代码、网页、文档、数据、图片、演示文稿、视频。

将这些维度与分类分离，可以避免一个 Skill 被迫放入大量交叉分类，也便于 Meilisearch 使用 facet 实现组合筛选。

## 5. 关键产品决策

### D-01：兼容性按 Agent 建立独立记录

“支持 Skill”不是布尔值。同一个 Skill 在不同 Agent 上可能需要原生文件、格式转换、不同目录或只支持部分能力。正式数据应以 `Skill × Agent` 兼容性记录为准，并绑定验证环境和时间。

### D-02：安装采用方案 B

用户先选择 Agent，再展示专属安装命令、卸载命令、目标目录和格式说明。不能给出一条模糊的通用命令后让用户自行推断。

### D-03：不使用模糊总分

评测分别展示安装、任务效果、稳定性、安全、成本或人工干预等维度。不同维度不可简单压缩成一个总分，以免掩盖适用条件。

### D-04：安全结论必须可解释

风险等级必须伴随权限事实与原因。中风险不等于不安全，通常意味着需要运行命令、修改文件、联网或访问敏感资源。用户必须能查看具体原因。

### D-05：结论绑定版本与 Commit

兼容性和安全结论必须记录 Skill Commit、Agent 版本、模型、操作系统和验证时间。源仓库更新后，如果最新 Commit 与验证 Commit 不一致，应显示“结论可能已过期”。

### D-06：收藏分阶段实现

1. MVP：不登录也能收藏，保存在浏览器本地。
2. 登录后：支持跨设备同步、更新提醒和重新验证提醒。
3. 首选登录方式：GitHub OAuth。

未登录用户登录时应提供将本地收藏合并到账户的能力。

### D-07：MCP 暂不建立独立目录

MVP 在 Skill 详情页增加“依赖或搭配的 MCP”栏目，记录必需/可选、用途和配置说明。先观察内容量、搜索量和用户行为，再决定是否建立 MCP 专区。

### D-08：工作流是独立内容对象

工作流不是简单的 Skill 列表，需要保存顺序、每步目标、输入、输出、整体验证环境和组合风险。只有完成端到端测试的 Agent 才能标记为“整体验证”。

### D-09：正式站点以中文体验优先

中文是默认语言，英文为完整可切换版本。分类、状态等稳定枚举可使用机器键和本地化标签；长文本应作为 CMS 的本地化字段管理，避免继续维护平行静态文件。

## 6. 正式系统架构推导

### 6.1 职责边界

- **Next.js**：公开页面、SEO、服务端渲染、账户界面、收藏及提醒交互。
- **Strapi**：Skill、兼容性、评测、工作流、MCP 关系、编辑流程和媒体证据。
- **PostgreSQL**：Strapi 内容、用户关联、收藏、提醒偏好、同步状态和审核记录。
- **Meilisearch**：全文检索、拼写容错、排序和 facet 筛选。
- **后台任务**：仓库元数据同步、Commit 变更检测、搜索索引更新、提醒发送。
- **采集管线（CMS 前）**：`tools/skill-collect` 双通道（GitHub + 对标站）合并为 `content/drafts/*.draft.json`；结论字段仅人工填写后导入 CMS。详见 `doc/采集工作流.md`。

### 6.2 内容流

1. 采集管线从 GitHub / 对标站写入 JSON 草稿（元数据自动；兼容性/安全/评测结论留空待审）。
2. 人工审结论字段后，导入 Strapi 创建/更新 Skill 草稿（CMS 就绪后）。
3. 审核人员补充分类、兼容性、安全结论和来源。
4. 发布后触发 Meilisearch 索引更新。
5. Next.js 读取已发布内容并生成公开页面。
6. 仓库最新 Commit 变化时标记相关验证记录可能过期。
7. 评测完成后上传证据、发布报告并更新验证状态。

### 6.3 搜索流

搜索文档应扁平化包含：

- 中英文名称、描述、标签、关键词、作者和仓库。
- 分类、支持 Agent、兼容状态、验证状态、安全等级。
- API Key、付费、Shell、网络等布尔要求。
- 输出格式、最近验证时间、收录时间、安装量或热度。

过滤使用 Meilisearch facet；最终展示数据以 Strapi/PostgreSQL 为权威来源。

## 7. 风险与约束

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 演示数据被误认为真实结论 | 损害可信度 | 正式数据上线前持续显示原型标识；生产环境禁止导入演示结论 |
| Skill 更新导致结论失效 | 错误推荐 | Commit 监控、过期标记、重新验证队列 |
| 安全等级标准不一致 | 用户无法比较 | 建立权限字典、判定规则和人工复核清单 |
| 四个 Agent 变化快 | 安装说明失效 | Agent 版本化配置、定期回归验证 |
| 中英文内容不同步 | SEO 与体验不一致 | CMS 本地化工作流和发布完整性检查 |
| Strapi 与 Meilisearch 不一致 | 搜索到已下架内容 | 发布/下架事件驱动同步，加定期全量校验 |
| 收藏涉及匿名与登录两套状态 | 丢失收藏 | 设计幂等合并接口和冲突策略 |
| 评测证据可能含敏感信息 | 泄漏密钥或私人代码 | 上传前脱敏、访问控制、保留期与删除机制 |

## 8. 待确认事项

### P0 阻塞项

- **“第 3 项”原文缺失**：历史对话中两次出现“认可第 3 项”，但无法确认具体指代。产品负责人需要提供原文或直接描述要求。在确认前，不得将任何推测写入已承诺范围。

### 上线前需确认

- 正式首发数据规模及每个分类的最低内容量。
- “安装量”数据来源及统计口径。
- 低/中/高风险是否需要增加“高风险”状态；当前原型只有低风险、中风险、未评估。
- 评测证据公开到什么粒度，是否需要登录或脱敏下载。
- Skill 提交是开放表单、GitHub Issue，还是登录后的审核工作流。
- 更新提醒渠道：站内、邮件或两者。
- Strapi 用户体系与站点用户体系是否共享，或由独立认证层管理。
- 英文版是否首发同步上线，还是中文稳定后发布。

## 9. 从原型到产品的验证顺序

1. 先确认内容模型、评测标准和安全规则，而不是直接迁移页面。
2. 用少量真实 Skill 在 Strapi 跑通录入、审核、发布和更新。
3. 接入 Meilisearch，验证中文召回、双语搜索和组合 facet。
4. 将原型视觉组件迁移到 Next.js，并改用真实路由和服务端数据。
5. 跑通 Skill 详情、搜索、兼容性和安装命令这一条最短核心闭环。
6. 再迁移对比、评测、工作流、匿名收藏。
7. 最后接入 GitHub 登录、跨设备同步、提醒和投稿流程。
